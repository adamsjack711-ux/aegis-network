# Phase 4F-R agent-owned denial contract v1 — proposal

**Revised contract proposal only; no runtime/source/schema change.** Baseline `d15a3a756b8066c5cb2d98665662220e52f4a7d6`; agent-owned design `67433e52cf8dc8477c1c9a4a93fb5d8cfa133768`; VAL-R field review `8e731ae7582587eab035f573730b4b514ecdb45d`; Main field decision `docs/phase4f-r-field-contract-decision.md`; frozen agent-owned oracle `6c7589e87bcb000f4df0cbe3959d56edea3ea3b3`. External `a51e8a6` target-side denial remains a **separate protective hold**, never an agent decision. This document proposes private, opt-in local interfaces only. Existing signed Mesh and native T4/T5 bytes remain frozen; new encodings and authority semantics need Main and VAL-R approval before implementation. The five-second gate remains failed.

## Trust and scope rule

An agent may enter `unclaimed_deny_only` only as the restarted process of a pre-enrolled deployment, using its operator-pinned canonical SQLite audit store. It cannot connect to NATS, fetch Mesh traffic, ACK, move an ordinary/critical cursor, issue target commands, consume positive approval, emit an allow decision or reopen a route. It directly obtains the complete current native T4/T5 withdrawal view. It verifies the original signed Mesh revocation, issuer grant/scope, local inventory, local denial policy, exact Finding↔Evidence binding and current witnessed status **before** atomically committing its own `revocation_decisions` row, `revoked_targets` tombstone and proof provenance. A generic unknown-status hold is a different record and cannot score as an exact withdrawal denial. Target generation and target-side hold remain independent.

### 1. `AgentEvidenceMap.v1` — exact operator-approved mapping

Canonical body fields (strict, no extras): `kind="aegis.agent-evidence-map.v1"`; `deployment_id` canonical UUIDv4; `agent_id` same enrolled UUIDv4; `audit_store_id` random immutable UUIDv4; `target_id` enrolled local target name; `cohort`, `audience`, `operator_key_id` enrolled names; `finding_id` UUID; `finding_publisher_id` enrolled name; `finding_sha256` lowercase SHA-256 of **existing `artifact.canonical_bytes(Finding)`**, not wire JSON; `finding_sequence` positive integer; `bundle_sha256` lowercase SHA-256 of the canonical native Evidence bundle; `claim_sha256`, `material_scope_sha256`, `environment_sha256` native manifest digests; `inventory_snapshot_sha256`, `policy_snapshot_sha256`, `exact_plan_sha256` local immutable digests; `not_before_ms`, `expires_ms` UTC milliseconds with `not_before_ms < expires_ms`; `nonce` 32-byte hex. Envelope fields: `body`, `signature` base64 Ed25519 over `b"AEGIS-AGENT-EVIDENCE-MAP/v1\x00" + canonical_json(body)`. Canonical JSON is UTF-8, sorted keys, compact separators, no NaN, exact integer types; verification rejects duplicate JSON keys, noncanonical bytes, unknown fields, wrong key role, expired signature or reused nonce. This is a new domain-separated signature **using the existing Ed25519 library**, not a new cryptographic primitive.

The agent first retrieves the exact signed Finding from its locally pinned prior finding/audit record or independently verified T4 history, checks its existing signature and publisher grant, and verifies the stored `finding_sha256`, UUID, publisher and sequence. Mesh `Revocation` v1.1 must match the triple `(target_publisher_id, target_artifact_id, target_sha256)` exactly; v1.0 unbound publisher is **ineligible** for preclaim v1. The Finding must have **exactly one** Evidence reference. The current `phase3c.check_bundle` validates this mapping **only for the enrolled route-toggle fixture**: its exact `lab-reproduction` URI/digest and claim digest, plus hardcoded `lab-blue` cohort, `route-toggle` family, expected material objects, `pkg:generic/aegis-demo` at `1.0.0`, and `restrict-fixture-route.v1` template. Another package, material family, cohort, target or template needs a separately reviewed general native binder and cannot inherit this map. Multiple candidate bundles, URI-only claims or a same-UUID/different-body finding is `unknown`, not an accepted withdrawal. The native signed Manifest must match `claim_sha256 == digest_bytes(claim_bytes(finding))`, `environment_sha256` and `material_scope_sha256`; map, operator enrollment, local inventory/policy, T4 policy context/roster and T5 scope/authority pins must agree. A native Evidence withdrawal **without an exact signed Mesh revocation** blocks positive authority or triggers a separate hold but cannot create a Mesh `revocation_decisions` row. Map expiry is one of the earliest deadlines and does not extend a finding or grant.

### 2. `NativeT4WithdrawalDiscovery.v1` and `DirectWithdrawalSnapshot.v1` — proposed native discovery

This **requires a new native T4 interface**, independently reviewed before use. Current `/v1/journal/head`, `/consistency` and `/page` expose a sealed archive, which can omit a withdrawal accepted durably but not yet sealed. Current `/v1/journal/admission/{epoch}/{event}` requires the already-known event digest and cannot discover a coordinator-suppressed event. Native page size is 128. The 4E-C `/v2/withdrawals` and `phase4e.WithdrawalView` are shadow-only, cap a view at 256 records and are **never** authority inputs. The proposed endpoint lives under the native journal authority, not the 4E-C service; its route, version and bytes are subject to separate review.

`DiscoveryRequest.v1` fields: version/domain, enrolled `deployment_id`, `agent_id`, `audit_store_id`, `cohort`, `audience`, hash of locally pinned T4 policy context and four-operator roster, previous independently anchored per-witness `(size, root)` floor, 32-byte request nonce, UTC issue time and local maximum clock error, and page size 1–128. The request is authenticated as the enrolled workload and bound to that agent's authority scope. It contains **no coordinator-supplied revocation ID**. Query every pinned native T4 witness directly. The witness must atomically append each admitted Mesh revocation's *original signed envelope*, historical grant/admission context and an accountable acceptance record to a durable, append-only native withdrawal-obligation stream before acknowledging its acceptance. `NativeDenialAcceptance.v1` is a new witness-signed record over T4 context, witness ID, exact envelope digest, original issuer/key/sequence, admission epoch, obligation ordinal/root and protected monotonic witness floor. The durable append and protected floor must precede its receipt; a receipt without the matching authenticated page and consistency proof is unusable. An accepted but unsealed obligation must be discoverable. The witness signs a challenge-bound immutable `DiscoveryHead.v1`: witness/roster/key IDs, T4 policy context, request nonce hash, obligation stream root/size, prior floor, signed UTC issue/expiry, and response domain. Pages bind that head, carry 1–128 dense ordinal positions, exact canonical source bytes or their authenticated inclusion path, inclusion proofs and a `next_position`; the final page carries an authenticated terminal position equal to the signed size. Consistency proofs connect the head to the agent's independently anchored floor. All pages for one witness must use the **same** head. New native records use strict canonical UTF-8 JSON and distinct domain-separated Ed25519 messages, for example `aegis-native-t4-denial-acceptance/v1\x00` and `aegis-native-t4-discovery-head/v1\x00`; byte encodings, error codes and test vectors require independent review before implementation. A bounded maximum page count/bytes and resource budget must be published in the policy; exceeding it is `unknown`, not truncated success. Ordinary 1,000-finding backlog must not starve this critical query.

`DirectWithdrawalSnapshot.v1` is the locally appraised aggregate of four such fresh, authenticated, complete native views and both separate T5 status responses. The agent verifies every ordinal from its anchored floor through each signed head, rejects a missing/duplicated page or terminal, failed inclusion/consistency, stale or reused nonce, rollback, equivocation, unknown key/context, incomplete response and clock uncertainty. It filters exact signed target triples locally. The first witnessed, durable acceptance of an exact scoped signed Mesh Revocation 1.1 may precede **denial only** when an independently anchored native obligation receipt from a pinned witness is included in a complete current view, native historical issuer authorization at the admission epoch and current compromise/revocation rules validate, and all four views are fresh and complete. One witness's signature alone is not a native positive cut or arbitrary denial authority: it cannot invent a publisher's valid scoped signed revocation. The native 3-of-4 sealed cut remains the positive-history rule. A malicious witness's unanchored or stale claim, a third-party report and a coordinator assertion never count. Acceptance/quorum, obligation-anchor custody, issue/expiry budgets and 1-fault assumption require an independent native T4 protocol review; the existing `Admission`/`Receipt` types do not encode this proposed single-witness deny-only acceptance.

T5 is **Evidence status, not Mesh revocation status**. `RelyingStatus.evaluate` uses two pinned status witnesses for the exact bundle, claim and scope. T5 may still return `reproduced` after a valid Mesh revocation; that does not negate T4's deny-only scoped revocation. Conversely, T5's `inconclusive`/`revoked` reason requires a separate signed Evidence withdrawal of the exact bundle, attestation or verifier key; it is a separate positive-authority block and does not create a Mesh `revocation_decisions` row. A `reason` string such as `"mesh-withdrawn"`, a shadow withdrawal view or a prior positive T5 result cannot bridge these namespaces. The agent records current T5 policy hash, exact scope, both operator identities and signed source digests. A required native T4 view or T5 operator unavailable, stale, equivocal or contradictory yields `unknown/conflict`: block new positive writes and permit only a separately labeled locally authorized hold, **no exact `REVOCATION_ACCEPTED` row**. Recheck every signed and local deadline after the final network read and immediately before SQLite commit.

### 3. Local snapshot and `VerifiedAgentWithdrawal.v1`

An operator-signed `AgentAuditEnrollment.v1` pins `deployment_id`, `agent_id`, `audit_store_id`, workload principal/credential key pin, canonical resolved DB path, independently attested host and volume identities, target roster digest, executable/schema profile, initial external audit-anchor root/sequence and allowed direct T4/T5 policy/context and authority key pins. The operator enrollment and credential binding, not `agent_id`, a copied UUID/path or a coordinator claim, select the one canonical store. The local agent records a signed or hash-pinned `InventoryPolicySnapshot.v1` with immutable snapshot ID, full sorted `(purl, version)` inventory and digest, policy version/digest, exact previously protected finding/plan/target list, local authorization expiry and operator key pin. It re-reads and hashes the full snapshot after the last blocking T4/T5 call and before commit; partial, changed or stale inventory/policy cannot produce a specific accepted denial. The no-broker-lease phase must never rely on coordinator-provided inventory or plan.

`VerifiedAgentWithdrawal.v1` is a **local result**, not a remote authorizing message: `withdrawal_id`, original canonical signed Mesh revocation bytes/digest and key ID; issuer grant digest/role, admission epoch, revocation target triple and sequence; `AgentEvidenceMap.v1` digest; native T4 policy context/roster hash, anchored acceptance receipt, complete four-view heads/roots/sizes/floors and page/consistency proof digests; current T5 policy hash, exact Evidence scope, two status-operator endpoint/key IDs and signed source digests, contradiction result and earliest expiry; request/response nonce, audience and workload identity; inventory/policy snapshot IDs/digests; local UTC lower/upper sample, clock-error upper bound and process-local `validated_until_ns`. Preserve distinct T4 and T5 freshness bounds and derive the effective deadline as their minimum with signed event/grant/map/policy expiry. An original revocation signed by an expired/revoked key, out-of-scope issuer, invalid sequence or wrong body fails before this result exists. The local result must be revalidated against the pinned source bytes rather than trusted because it serializes consistently. A persisted monotonic deadline is audit telemetry only; after process/host restart a new clock sample and independent appraisal are mandatory.

### 4. Atomic agent-owned SQLite decision

The proposed opt-in audit profile adds `audit_contract_version=2`, immutable `audit_store_id`, and `revocation_provenance_v1(event_id PRIMARY KEY, event_digest, map_digest, signed_wire_sha256, issuer_grant_digest, t4_context_digest, t4_receipt_digest, t4_snapshot_digest, t5_policy_digest, t5_scope_digest, t5_status_digest, inventory_snapshot_sha256, policy_snapshot_sha256, local_clock_error_ns, validated_until_ns, audit_anchor_floor, decision_digest)`. The existing `revocation_decisions` and `revoked_targets` tables remain the frozen independent oracle. Under one `BEGIN IMMEDIATE` transaction on the **enrolled canonical agent database**, check `audit_identity`, store ID, schema profile, local snapshot and post-I/O proof freshness; insert exactly one authenticated `revoked_dry_run` / `REVOCATION_ACCEPTED` row with original publisher, sequence, target triple and digest, one exact `revoked_targets` tombstone, and matching proof provenance. Derive a versioned local decision hash from the exact three records and append it to a local audit hash chain in the same transaction. An `INSERT OR IGNORE` tombstone or same-UUID body change is an error, not success. Commit with SQLite durability settings explicitly verified in the disposable fault harness. If the process dies before commit, none of the three rows exists; after commit, all three do. A separately opened read-only SQLite connection, not a worker log or HTTP result, scores the row. Persist only signed public wire and proof digests; credentials, private keys and bearer tokens never enter this table, event payloads or structured logs.

Idempotency key is `(agent_id, withdrawal_id, SHA256(canonical Revocation payload), target_publisher_id, target_artifact_id, target_sha256)`. A same-key replay may return the existing decision **only after comparing every signed byte, target field, proof map digest and local store identity**; differing bytes for the same UUID or reused publisher sequence cause conflict/hold, not `INSERT OR IGNORE`. Two incumbent/replacement processes sharing the canonical database must serialize through SQLite and yield one logical row. A stale agent with a different cloned database cannot produce a scored denial because independent enrollment and audit-anchor checks reject that store. `critical_recovery_cursor` and `recovery_cursor` are neither read as proof nor advanced in this transaction. Later owned replay may advance a generation-bound cursor after it verifies the committed decision/provenance; a broker ACK follows that step and never grants authority.

### 5. Rollback anchor, readers and migration

An `AgentAuditAnchor.v1` is a separate operator-enrolled append-only, independently witnessed high-water mark: `deployment_id`, `agent_id`, `audit_store_id`, audit sequence, hash of ordered `(event_id, event_digest, target triple, decision_digest, provenance_digest)` rows, previous anchor root/size, signed checkpoint/consistency proof, signer roster and independent custody domain. The local SQLite also stores its last accepted root/size. The operator pins anchor authority keys and an external durable floor in a custody domain outside the agent host, its snapshots and broker; an agent cannot select a different anchor by changing a path or UUID. Anchor ingestion authenticates the enrolled workload, binds the exact local hash-chain extension and returns a signed receipt. On startup and before any positive recovery, direct independent anchor views must be consistent and at least as high as the enrolled external floor; a restored older SQLite snapshot or two divergent copies cause hold and signed-journal reconstitution, never reuse of an old positive decision or silent tombstone deletion. A newly committed negative row may be visible locally before the external anchor is sealed; **positive** authority remains blocked until it is anchored or independently reconciled. If the agent/anchor stores can be rolled back together, an old host can impersonate the workload, or the anchor is unreachable, rollback resistance is unproved and the deployment remains held. Local Docker volumes with different keys do not prove independent custody.

Older workers do not understand `audit_contract_version=2`, native proof provenance or preclaim decisions. Migration is operator controlled: (1) pin and verify the canonical agent/store/host enrollment and independent anchor; (2) stop and exclude all profile-1 executables and credentials from this store, its broker consumer and the protected target; (3) verify target-home generation fence and deny-only hold; (4) take a consistent backup and verify existing tombstones/decision hashes; (5) in a single SQLite migration transaction add profile marker, provenance and chain tables and new uniqueness/conflict constraints, preserving old table names, columns and rows; (6) start only enrolled profile-2 code, verify anchor continuity and reappraise native T4/T5 before any positive recovery. Merely adding a column is insufficient because current old code ignores unknown tables. A profile-1 process opening profile-2 SQLite for write must fail at a file/credential/process barrier **outside the schema**; a SQLite trigger alone does not secure arbitrary old writers. An old read-only diagnostic may display a negative row but cannot turn it into current native authority, ACK as a successor or clear it. A new worker reading legacy rows must label them legacy/dry-run, reverify exact signed bytes and native proof before adding provenance, and never silently upgrade a row because its UUID matches. Mixed-version writer, consumer or restored snapshot without the complete barrier stays restrictive and ineligible. Preserve original signed Finding 1.0 and Revocation 1.0/1.1 bytes and publisher ordering for existing readers; preclaim v1 accepts only exact publisher-bound Revocation 1.1. Unsupported new profile fails closed rather than falling back to Mesh-only denial.

## Reader and fault matrix before adoption

| Reader / store | Proposed rule |
| --- | --- |
| Old agent + old store | Continue existing fail-closed Mesh dry-run behavior; no preclaim proof or authority claim. |
| New agent + old store | Read-only migration assessment first. Existing rows remain `legacy` until exact source and native proof are revalidated; do not retroactively count them toward the new five-second test. Operator-enrolled migration writes profile 2 only after all owners/consumers are fenced. |
| Old agent + profile-2 store | **Must be prevented** by operator-controlled executable enrollment, file access and target/consumer generation barrier. Current old `SqliteAudit` ignores unknown tables, so an additive schema alone is unsafe. If the old binary can open/write this store, profile-2 activation is NO-GO. |
| New agent + profile-2 store | Verify enrollment, audit-anchor continuity and local snapshot, then deny-only direct discovery. Normal broker consumption starts only after a valid current owner claim and generation-specific cursor reconciliation. |
| Restored snapshot or cloned UUID/store | If local sequence/root is below the independent anchor or store/host enrollment conflicts, hold positive authority and rebuild from independently witnessed signed history. A clone's row is never counted for the original agent. |

Proposed exact negative and control cases, to be run against an independently reviewed native T4 endpoint rather than the current 4E-C shadow endpoint:

| Case | Required observation |
| --- | --- |

A crashed/unreachable agent, unavailable required witness view or inaccessible canonical audit store is missed/censored, never replaced by a target proxy or omitted.
