## Verification and storage

The handoff invokes `verify_investigation` before writing. It rehashes the supplied source bytes, derives the deterministic disposition again, resolves the expected v2 reference set for the source rows and rechecks exact excerpt spans. VAL independently checks whether the referenced row actually supports the specific package/version decision. The handoff alone writes the research result to the disposable Scout SQLite database. It acquires the SQLite writer lock, rechecks the current sequence, advisory and digest, and commits at most one result per sequence, vulnerability ID and asset digest. Stale or withdrawn work is held. Historical payloads remain intact when their revision is superseded or withdrawn.

`read_history(path, source_kind, advisory_id)` opens initialized SQLite in read-only mode and returns one fresh committed snapshot in stable order. Each row keeps the stored v1/v2 payload and joins the revision's current status. Reading history carries no new verification. The record stays private research with `independently_verified=false`. Result types and consumers remain confined to local research reporting. The workflow has zero execution, network, signing, Mesh, Evidence, approval, mitigation, Runner or protected-writer authority.

## Later live experiment gate

Prior scripted experiments measured guard behavior and metadata matching. Scripted token counters are zero and billed cost is unmeasured. Any live experiment needs independent, explicit approval for the endpoint/model and the exact content permitted to leave the lab, including source rights, sensitive-data review and retention.
