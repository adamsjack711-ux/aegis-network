# Phase 5C-1 provisional diagnostic contracts

**Revised after VAL-1 review `20d4e187cda1e0854c60ee830c49af52c81ed389`; for interface review, not implementation approval.** These are private `proposal-v0` records. None is a signed Mesh Finding, Evidence record, verifier attestation, status endorsement, local mitigation approval or executable artifact. The authoritative contracts remain `SignedFinding 1.0`, exact `InventoryItem(purl, version)` matching and native T4/T5. The Diagnostic Runner has no reader or writer in those authority paths.

## Proposed records

All request/result JSON would be strict UTF-8 with duplicate-key rejection, no NaN, unknown-field rejection and declared byte limits. A digest covers canonical serialized bytes for correlation; no unkeyed hash is called an authenticated signature. Version changes receive new `kind` values and old/new reader tests. Initial **hard local-lab ceilings** are request ≤64 KiB, sealed input ≤1 MiB, worker result ≤1 MiB, sanitized stderr ≤4 KiB, wall deadline ≤3 s, CPU ≤1 s, hard cgroup memory ≤256 MiB (swap disabled or capped with it), cgroup pids ≤4, per-worker open file descriptors ≤32, one CPU, private tmpfs ≤8 MiB and zero host output without a separate output capability. The launcher owns aggregate cgroup accounting and kill/reap; `RLIMIT_AS` alone is insufficient. Any profile may narrow these limits, never raise them through request data. The values are design caps until pinned Linux fixture and independent trials verify they are achievable.

| Record | Required fields and interpretation |
| --- | --- |
| `DiagnosticTargetEnrollment.proposal-v0` | `kind`, opaque stable local `target_id` without hostname, disposable fixture ID and immutable image/root digest, enrollment digest, permitted profile IDs, preopened pathname root identity, `not_before`, `expires_at`, `network=disabled`, `writes=none`, exact scope and local administrator identity. It is pinned in an administrator-controlled local registry, not supplied by Mesh or research. Enrollment creation/revocation and registry integrity require separate review; expiry and a revocation floor are checked at each run. |
| `DiagnosticProfile.proposal-v0` | `kind`, profile ID/version, source-reviewed registry digest, pinned worker/image bytes digest, accepted input grammar and limit, fixture family, positive/negative control IDs and expected results, bounded output schema, limits, deterministic parser revision, `side_effects=none`. It contains no shell command, download URL, dynamic module name or remote script. Only installed registry entries are selectable. |
| `DiagnosticRequest.proposal-v0` | `kind`, unique run ID, exact target-enrollment digest, sealed-input digest, selected profile ID/version/digest, bounded local invocation time and requested budget ≤ profile ceiling. **No `operator-invoked` bit, bearer token or output path.** The launcher also requires an out-of-band, nonserializable one-use local run capability; its sealed-input digest is bound before the broker consumes it for launch. A copied JSON request alone always rejects. A research candidate can only display a suggested profile ID. |
| `DiagnosticObservation.proposal-v0` | `kind`, run ID, target/profile/sealed-input digests, worker/image/containment profile digest, launch and finish UTC correlation times, same-host monotonic stage spans, bounded CPU and peak aggregate RSS, control observations, outcome, reason code, partial/complete flag, parser revision and sanitized result digest. `independent_status` is the **literal `"unknown"` in every proposal-v0 result**. A native proof adapter needs a new schema version and separate review. No action, mitigation, approval or `verified=true` field. |
| `DiagnosticTranscript.proposal-v0` | Ordered run-stage hashes for preflight, launch, result read, validation and disposal, plus source commit/image pin and a local transcript digest. Optional explicit output capture records the chosen destination and file digest. A local transcript does not establish independent custody or successful host cleanup without separate observation. |

The out-of-band local run capability is minted by a trusted local authorization broker only after an explicit operator invocation, peer-credential and administrator-owned enrollment checks. It is a one-use connection/descriptor handle bound initially to run ID, target, installed profile, budget and short expiry. The launcher seals the selected input; the broker binds its digest and consumes the grant atomically before launch. The broker keeps one-use state in memory, invalidates all handles on restart, and rejects handles from previous broker epochs; no default persistent write is needed for this grant. The handle is never serialized, accepted from an advisory or logged. Losing the session invalidates it. Same-UID malicious callers and administrator compromise are residuals requiring OS and enrollment review. The optional **output capability** is minted separately by the same trusted local operator path: a preopened private directory descriptor plus fixed leaf identity and one-use create right. The launcher uses descriptor-relative exclusive/no-follow creation and rejects ancestor/final symlinks and races. A request field cannot nominate an arbitrary output path. The default emits to stdout and writes no persistent host file.

The selected input is copied through descriptor-relative lookup under the enrolled root into a private Linux sealing-capable memory descriptor. The launcher checks the source descriptor identity and metadata before and after copying, seals write/grow/shrink/further seal changes and hashes the sealed bytes; the worker receives that descriptor and independently verifies seals and digest before parsing. A mutable host read-only bind and a prelaunch hash alone are insufficient. The worker never reopens a host path. Missing seal support, source replacement or digest disagreement rejects the run.

### Containment profile to pin before implementation

Candidate cached image ID: `sha256:f4d96476e0c78b0a45c25acaed6cfc770e469058d23c888ae0e14047f89eebab` (the prior independent 5B Kali arm64 fixture, **not** 5C acceptance). The fixture manifest must pin its actual `docker image inspect` ID, Linux/kernel version, worker bytes, namespace and mount configuration, exact seccomp JSON bytes and SHA-256, cgroup limits, and the tracer binary/version/SHA-256. Proposed execution flags: `--pull never --network none --read-only --user 65534:65534 --cap-drop ALL --security-opt no-new-privileges --pids-limit 4 --cpus 1 --memory 256m --memory-swap 256m`, plus an 8 MiB private tmpfs, no host write mount, user/mount/PID/network namespaces and a custom second-stage seccomp filter installed before reading input. The initial reviewed launcher-to-worker exec is the sole permitted exec; worker `socket`, `connect`, `bind`, second `execve/execveat`, fork/clone and privilege syscalls must be denied and independently observed. Bounded writes to stdout/stderr and the private tmpfs are necessary; no host-writable descriptor may enter the worker. Mount and descriptor isolation, rather than a generic `write` syscall ban, prevent host writes. A default Docker seccomp profile or Python audit hook does not satisfy this rule. Candidate independent observer is Linux `strace -ff -qq` with a reviewed explicit set of network, process, file and credential syscalls; the exact command and binary digest must be pinned before testing, and trace files stay outside the worker. If tracer or permission is unavailable, the attempted-effect gate is unverified and preview NO-GO. The seccomp bytes and tracer digest are **not yet available** and block implementation intake.

`outcome` is one of `observed`, `not-observed`, `inconclusive`, `rejected`. `not-observed` means this *specific registered check* did not see its marker under passing controls; it is not `unaffected` or `safe`. `inconclusive` covers unavailable target, failed/absent controls, timeout, truncated output, resource denial and incomplete snapshot. `rejected` covers invalid enrollment, unsupported profile, malformed request, mismatched digest or attempted scope escape before a valid observation. Each non-`observed` result has a stable reason code; success cannot be inferred from process exit 0 alone. An error result remains in the planned-run denominator.

## Frozen adapters and compatibility

| Producer → consumer | Proposed handling |
| --- | --- |
| 5A research → 5C | Optional, untrusted `suggested_profile_id` and source span only. Operator must independently select an installed profile and locally enrolled fixture and obtain the out-of-band one-use run capability. No model tool call or automatically accepted request. |
| 5B CLI → 5C | No default call or import. A future explicit local-lab command would display the DiagnosticObservation with its provisional kind, exact target scope, controls and unknown independent status. 5B owns CLI UX and package metadata. |
| 5C → existing `SignedFinding 1.0` | **No adapter.** `SignedFinding.model_validate` must reject a diagnostic result. A publisher may later research it, but must use the existing independent Evidence and signing pipeline. |
| 5C → native Evidence/T4/T5 | **No adapter.** Existing Evidence schemas must reject it; a registered verifier must independently reproduce a pinned Evidence bundle through native rules. A diagnostic transcript is not an attestation, withdrawal or status endorsement. |
| 5C → local approval, Rapid or protected writer | **No reader.** The output is inert even if its digest or local audit transcript validates. Unknown/stale/conflicting Trust remains a protected-write denial. |
| Old readers | Existing CLI/Evidence/Mesh readers ignore or reject the new kind; no reinterpretation of `vulnerability_id`, signed evidence refs, package ranges or exact inventory equality. |

The proposed local enrollment and run capability must not be confused with native ownership generation or a target action lease. They permit one observation of an inert disposable fixture only; they neither bypass 4F fencing nor extend local approval expiry. The default output does not disclose hostnames, network addresses, process arguments, credentials, source documents or raw environment variables. If later diagnostics need any of those, update the privacy and data-flow review before code.

## Versioned review checklist

Before adopting a contract, the integration lead and VAL-1 should require golden canonical bytes, duplicate-key/unknown-field/oversize negatives, old/new reader rejection, explicit enrollment scope and expiry, exact profile and image hash checks, result-state semantics, deterministic control failures, safe cancellation and resource-bound proofs. An authority bridge would additionally require independent T4/T5, SignedFinding and local-policy review. No authority bridge is proposed here.
