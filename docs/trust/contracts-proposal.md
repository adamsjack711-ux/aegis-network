# Aegis Trust contract proposal

**AT-01 · Proposed, isolated lab only.** Review with Mesh, Rapid, Evidence, Mitigation and the security review lead against Phase 4's contract freeze. The prototype introduces a separate namespace. It imports the existing canonical JSON and hashing helpers, preserves the Phase 3C APIs and signed bytes, and keeps legacy auth and event delivery on their existing paths. ## Prototype encodings

All prototype signed bodies use the existing compact sorted ASCII JSON encoder and domain-separated Ed25519 signatures from `cryptography`. The bytes start with `AEGIS-TRUST-LAB/v1`, a NUL, the record domain, a NUL, and the canonical body. Signature and SHA-256 values are lowercase hexadecimal. The root uses a pinned 2-of-3 key quorum to sign an adjacent chain of delegated grants. It carries predecessor body digests and expiry. The prototype fixes root and witness memberships for the life of the fixture. Existing Aegis Finding, revocation and Evidence bytes keep their original signature domains.

For a three-record cut sealed through epoch 100, the lab checkpoint fields are `{"epoch":100,"root":"<sha256>","scope":"synthetic-blue","size":3,"trust":"<sha256>"}`. The root commits to the ordered vector of admission bodies. Each body commits to the exact signed event and carries a 3-of-4 admission certificate. The archive includes signed events and receipt signatures. The coverage body contains this checkpoint and a 256-bit nonce. The Evidence response adds the same nonce and has version 101 and expiry tick 102. Real digest and nonce values are generated by the synthetic tests. Production canonicalization and transport should ship published golden vectors and strict bounded decoding before any interoperability claim.

## Compatibility and rollback

| Reader or writer | Behavior |
| --- | --- |
| Phase 3C reader with Phase 3C wire | Existing dry-run and isolated lab paths continue to use the reviewed contracts. Existing tombstones and decision history remain readable. |
| Phase 3C reader with proposed trust records | Keep these records off existing subjects and endpoints. Existing transport schemas and rejection behavior remain unchanged. |
| Trust shadow reader with mixed delivery | Translate via a locally governed mapping after checking original wire signatures and scopes. Treat legacy replay events as hints. Produce hypothetical decisions and checkpoint audits without target access. |
| Trust writer with unsupported or missing Trust records | Enter hold. Local exact approval and evidence from a prior decision cannot reopen a target. |
| Pilot downgrade or rollback | Stop new Trust writes, fence the active generation, and retain the strongest verified denial/restriction, trust and checkpoint floors, and audit. Resume only through an explicitly authorized migration or a fresh compatible Trust reconciliation. |

Approval requires schema and lifecycle review, canonical vectors across implementations, mixed-version decisions, retention and restoration tests, an admission/coverage outage plan, and explicit owner sign-off. The proposal introduces no new production route or wire field.
