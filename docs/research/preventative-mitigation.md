# Aegis R2 — Preventative Mitigation Engine

*Research proposal · 2026-11-19*

Define which effects a workload should never produce, then enforce those limits before serving traffic. Aegis would bind a reusable profile to a concrete deployment, check what its local controls can enforce, and require independent evidence that the named effects are blocked and legitimate work still succeeds. Start with **native policy compilation**. Evaluate **live runtime enforcement** where restarts make rollout too slow, and **isolated workers** where the shared host kernel or broad workload authority is the main concern. The architectures, format and experiments below are proposals. The current Aegis slice validates signed findings and records local dry-run decisions. [Aegis architecture](../../architecture.md), [acceptance plan](../acceptance.md).

## What can be protected before discovery

Build profiles from a workload's intended privileges, files, peers and features. Workload owners define which effects are forbidden even if a component were to misbehave. Examples include a renderer altering another workload's state, connecting to an administrative service, or starting a process outside its task. Model partial or full loss of control of the application process while the enforcement boundary, administrators and verifier remain trusted. Edge and flag controls address narrower request- and feature-level claims. The trust boundary matters because arbitrary code inside a compromised process may ignore an in-process flag. [NIST Application Container Security Guide](https://csrc.nist.gov/pubs/sp/800/190/final), [OpenFeature evaluation specification](https://openfeature.dev/specification/sections/flag-evaluation/).

| Control | What it can prevent | What determines coverage |
| --- | --- | --- |
| Application sandbox and least privilege | A dedicated non-root identity, dropped capabilities, no privilege escalation, read-only root, narrowly scoped writable mounts and credentials, namespaces and resource limits constrain host access and blast radius. Assign separate credentials and storage to auxiliary workers. | Shared-kernel containers still depend on the integrity of the host kernel. Writes to allowed volumes, disclosure through allowed credentials and resource use within quotas remain possible. [Kubernetes Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/), [NIST container security guidance](https://csrc.nist.gov/pubs/sp/800/190/final). |
| seccomp | Filter system calls by ABI, call number and supported scalar arguments. Use a runtime-default filter as the starting point and a reviewed workload-specific allowlist where it adds useful restrictions. | Filters cannot dereference pointer arguments or express a file pathname policy. Bind profiles to Linux architecture and runtime, cover startup and maintenance calls, and replace workloads when changing a Kubernetes launch-time filter. [Linux seccomp documentation](https://docs.kernel.org/userspace-api/seccomp_filter.html), [seccomp in Kubernetes](https://kubernetes.io/docs/reference/node/seccomp/). |
| AppArmor and SELinux | AppArmor profiles mediate resources such as file paths and capabilities. SELinux type enforcement mediates access between labeled subjects and objects, including storage shared across services. | Verify a loaded, enforcing AppArmor profile and the relevant mount paths. For SELinux, verify enforcing mode, process and object labels, volume relabel behavior and policy on each eligible node. Treat AppArmor complain and SELinux permissive as observations. Translation requires an explicit mapping because pathname and label semantics differ. [Kubernetes Linux security constraints](https://kubernetes.io/docs/concepts/security/linux-kernel-security-constraints/), [Red Hat SELinux guide](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html/using_selinux/getting-started-with-selinux_using-selinux). |
| eBPF | A supported pre-operation LSM denial can prevent a kernel-mediated effect. An appropriate network attachment can enforce a separate packet or connection claim. | Verify kernel features, hook, attachment, scope and restart behavior per node. Trace events and asynchronous process kills cannot establish that a side effect was prevented. An inline denial must run before the effect and cover every relevant path in the claim. [Linux BPF LSM documentation](https://docs.kernel.org/bpf/prog_lsm.html), [Tetragon enforcement semantics](https://tetragon.io/docs/concepts/enforcement/). |
| Network restrictions and service isolation | Default-deny ingress and egress, permit only necessary peers, ports and DNS, and use authenticated workload identities and service authorization for operation-level decisions. | NetworkPolicy needs a supporting CNI. Kubernetes policies grant additive allowances, and established connections require provider-specific checks. Validate alternate routes, direct origin, host-local paths and IPv4/IPv6 where in scope. Identity-aware authorization also depends on authenticated identity and traffic traversing the enforcement point. [Kubernetes NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/), [Istio security practices](https://istio.io/latest/docs/ops/best-practices/security/). |
| WAF rules and feature flags | A WAF can reject requests outside a stable method, route, size or content contract on inspected HTTP ingress. Generic rules such as CRS can supplement that contract. A prewired flag can disable an optional operation on all its supported entry points. | Scope WAF claims to inspected routes, protocols and body limits, with explicit origin isolation and false-positive tuning. Pin safe SDK defaults and verify provider outage, stale cache and worker or scheduled entry points for flags. A route-level shutdown can hold the restriction at a separate boundary. [OWASP CRS anomaly scoring](https://github.com/coreruleset/documentation/blob/main/content/2-how-crs-works/2-1-anomaly_scoring/index.md), [OpenFeature flag evaluation](https://openfeature.dev/specification/sections/flag-evaluation/). |

Reusable profiles should describe workload roles such as renderer, read-only API or export worker. Start with an owner-approved inventory of required behavior across startup, steady state, jobs, maintenance and shutdown. Static analysis and observed traces can suggest tighter scopes. Review every suggested allowance against the workload contract before adding it. Rare code paths may be absent from a trace, and a trace can include activity the owner never intended to authorize. Revalidate on image, architecture, runtime, dependency or policy changes. [Confine policy-generation research](https://www.usenix.org/conference/raid2020/presentation/ghavanmnia), [Security Profiles Operator](https://github.com/kubernetes-sigs/security-profiles-operator).

## Three architecture options

All three use local authorization of exact profile and binding digests. The profile publisher, local deployer and independent verifier have distinct roles. A coordinator may distribute signed metadata. Local inventory, trust, allowlists and compatibility checks determine whether a narrowly scoped adapter can make a change. The verifier can read policy attachment and fixture outcomes with separately scoped credentials. Its results are bound to the deployment it actually tested. This extends the current Aegis trust model and depends on the existing execution gates. [Aegis architecture](../../architecture.md), [acceptance plan](../acceptance.md).

| Architecture | Enforcement and rollout | Main tradeoff |
| --- | --- | --- |
| **A. Compile to native deployment policy** | A deterministic compiler resolves the profile and local bindings to native manifests and a coverage plan. Use Pod security settings, seccomp, an available AppArmor or SELinux mapping, NetworkPolicy and explicitly scoped gateway or flag configuration. Validate target capabilities and effective policy, then admit a new replica with the required controls attached before serving. Canary via staged traffic, with a previous verified deployment revision available for fallback. [Kubernetes Linux security constraints](https://kubernetes.io/docs/concepts/security/linux-kernel-security-constraints/), [Argo analysis](https://argo-rollouts.readthedocs.io/en/stable/features/analysis/). | Smallest new privileged footprint and easiest configuration review. Replacing replicas and waiting on several controllers can dominate time to protection. Admission and readiness need to guard against scheduling on nodes with missing profiles. |
| **B. Enforce live with scoped node and gateway adapters** | Keep a launch-time least-privilege floor. Preinstall a bounded set of native enforcement adapters, such as CNI policy and supported eBPF LSM controls, and apply preapproved typed policy revisions to running workloads. Stage independent changes under a restrictive guard, confirm loaded revisions per endpoint, then probe before expanding. Keep the previous verified revision locally for recovery during control-plane loss. [Linux BPF LSM documentation](https://docs.kernel.org/bpf/prog_lsm.html), [Tetragon persistent enforcement](https://tetragon.io/docs/concepts/enforcement/persistent-enforcement/). | May improve activation time without restarting workloads. Privileged host components increase risk, hook semantics vary, and cross-adapter changes can partially apply. Restrict adapters to known policy types and workload scopes and treat unverified gaps as unresolved. |
| **C. Place risky operations in isolated workers** | Route parsing or conversion to a dedicated worker in an application-kernel sandbox such as gVisor or a dedicated-guest-kernel microVM. Supply bounded inputs and outputs through an authenticated broker, with no standing workload secrets and externally enforced network constraints. Enforce worker and gateway profiles separately. Verify the broker, worker and authorized outputs before routing traffic. A safe fallback can stop dispatching that operation. [gVisor security architecture](https://gvisor.dev/docs/architecture_guide/intro/), [Firecracker project](https://firecracker-microvm.github.io/). | A meaningfully different isolation boundary for selected tasks at the cost of a worker contract, extra hops, startup and capacity overhead, and more lifecycle work. Placement still depends on trusted host, broker, identity and output controls. |

Architecture A is the first pilot because it can quantify the value of the profile format and verification loop using existing enforcement systems. Evaluate B against A on the same controls and workload where semantics match. Evaluate C with the same worker contract across its trial arms so the effect of isolation can be distinguished from the effect of refactoring.

## Proposed portable profile v1

A profile is a closed, typed JSON document that describes required outcomes and how to verify them. A separate, locally authorized binding resolves logical names to exact image digests, workload and tenant identities, adapter versions, authorized peers and probe fixtures. A binding also pins the verified fallback by digest. Compile per platform and emit an auditable plan with each outcome mapped to an enforcement point, a probe and a target population. The intent travels between platforms. Whether it can be enforced is determined for each binding.

```json
{
  "schemaVersion": "1.0",
  "kind": "MitigationProfile",
  "profileId": "org.aegis.renderer",
  "revision": 3,
  "selector": {"role": "renderer", "os": "linux"},
  "requirements": [
    {
      "id": "renderer-network",
      "type": "network.egress.allowOnly.v1",
      "peers": ["resolver", "job-broker"],
      "connectionScope": "newAndEstablished"
    },
    {
      "id": "renderer-state",
      "type": "filesystem.write.deny.v1",
      "resource": "protected-state"
    }
  ],
  "verification": {
    "prohibited": [
      {"requirement": "renderer-network", "probe": "forbidden-peer-v1", "expect": "no-sink-receipt"},
      {"requirement": "renderer-state", "probe": "protected-write-v1", "expect": "state-unchanged"}
    ],
    "required": [{"probe": "render-job-v1", "expect": "output-matches"}],
    "maxEvidenceAgeSeconds": 300
  },
  "rollout": {
    "stepsPercent": [5, 25, 100],
    "minSoakSecondsPerStep": 60,
    "fallbackRef": "verified-renderer-hold"
  }
}
```

- **Schema and compatibility.** `schemaVersion` versions the document contract. `revision` is a strictly increasing positive integer per `profileId` within its authorized publisher namespace, and published revisions are immutable. Validate a closed schema, including enumerated operation, expectation and scope values. Reject duplicate keys and requirement IDs, unresolved references, unknown versions or fields, empty probe sets, missing probes for individual requirements and invalid rollout values. Each requirement is mandatory, and canary steps increase to 100%. Introduce new semantics through an explicitly supported schema or operation version. Profiles contain registered names and typed parameters. Local registries supply adapters, bindings and probes.
- **Signing and local authorization.** Encode the signed envelope as `{signed, signature}`, with `signed` containing `kind: "AegisMitigationProfileRelease"`, `publisherId`, `keyId`, `issuedAt`, `expiresAt` and `profile`. Sign the UTF-8 bytes of the literal `AEGIS-MITIGATION-PROFILE-v1` followed by a NUL byte and the RFC 8785 canonical JSON of `signed`, using Ed25519 with base64 encoding for the signature. Use RFC 3339 UTC timestamps. Store the profile payload's SHA-256 digest over its canonical JSON. Pin signer and role locally, and enforce validity, revocation and an authenticated revision watermark before accepting updates. Bind local approval to the profile digest, binding digest, compiled plan digest and target generation. Use a fresh, higher local deployment generation to authorize recovery to a pinned safe state without lowering a publisher watermark. [RFC 8785 JSON canonicalization](https://www.rfc-editor.org/rfc/rfc8785).
- **Operation semantics.** `network.egress.allowOnly.v1` allows only resolved peer/protocol/port tuples in both address families where enabled. `newAndEstablished` requires prohibiting traffic on existing disallowed flows, including draining or terminating those flows if the backend needs it. `filesystem.write.deny.v1` protects the resolved resource from content changes and replacement, including declared aliases and existing handles. For example, prefer mounting the resource read-only or omitting it where semantics permit. An AppArmor backend and a SELinux backend may satisfy the claim through different policies when appropriately bound and tested. If an adapter only covers new connections or path opens, the sample is unsupported on that target until coverage is established. [Kubernetes NetworkPolicy semantics](https://kubernetes.io/docs/concepts/services-networking/network-policies/), [Kubernetes Linux security constraints](https://kubernetes.io/docs/concepts/security/linux-kernel-security-constraints/).
- **Composition.** Combine requirements so each mandatory claim continues to hold. Treat multiple allow-only requirements as intersecting allowed sets and check denials against all effective policies, including externally managed ones. Reject a plan when target semantics cannot prove that composition, or when it conflicts with required transactions. A Kubernetes allowlist, for example, can be widened by a separate additive policy. Track `unsupported`, `observe-only`, `pending`, `verified`, `degraded` and `held` per target generation. Only fresh evidence for all mandatory checks yields `verified`. [Kubernetes NetworkPolicy semantics](https://kubernetes.io/docs/concepts/services-networking/network-policies/).

The two operation types above are sufficient to exercise v1 portability in the first pilot. Register additional typed operations for the broader experiments only with defined fields, attachment scope and oracle semantics. Candidate types include `service.call.allowOnly.v1` for authenticated callers on a named service operation, `http.request.requireContract.v1` for a named gateway route and request contract, and `feature.disable.v1` for a prewired gate with named entry points. Keep syscall filters, WAF expressions and native policy documents in the local adapter registry. This keeps their platform-specific semantics visible in the pinned plan. [Istio authorization policy](https://istio.io/latest/docs/reference/config/security/authorization-policy/), [OWASP CRS anomaly scoring](https://github.com/coreruleset/documentation/blob/main/content/2-how-crs-works/2-1-anomaly_scoring/index.md), [OpenFeature flag evaluation](https://openfeature.dev/specification/sections/flag-evaluation/).

## Verification, canaries and safe rollback

1. **Preflight.** Inventory all replicas, nodes, routes, long-lived sessions and jobs in scope. Verify kernel and runtime support, effective policies and current dependency access. Snapshot owned settings by resource version. Test the exact build and candidate policy in a disposable environment first, including readiness, cold start, upgrades, uncommon jobs and shutdown. Use shadow or audit mode to estimate disruption. Require enforced checks for a prevention claim.
2. **Canary and expand.** Prepare the restrictive fallback first. Keep unverified candidates away from relevant traffic until mandatory controls have attached and initial probes pass. A local reconciler serializes updates per workload scope, requires generation checks on writes, and records intended and observed adapter state so it can recover after a partial apply. Probe each path in the active generation, then expand in steps after the soak and health gates. Newly scheduled or restarted replicas re-enter verification before serving. A held path counts as disrupted if users expect that path to work. [Argo Rollouts analysis states](https://argo-rollouts.readthedocs.io/en/stable/features/analysis/).
3. **Use independent oracles.** A verifier built and operated separately from the deployer checks both the effective configuration and observable outcomes. Read fixture state or sink receipts outside the workload and outside enforcement telemetry. Include an unprotected positive control and a live sensor heartbeat, and correlate attempts and observations with unique trial IDs and a bounded observation window. The signed evidence should bind the profile, binding, plan, image, runtime, target generations, topology, probe-set digest, timestamps and coverage. Missing observation, stale evidence or mismatched generation suspends the protection claim. Reverify after reschedule, policy or provider change, and evidence expiry.
4. **Recover to a safe state.** On health regression, failed verification or loss of a required adapter, pause expansion under the restrictive guard. Restore a prior state only when it still satisfies the same prohibited-effect invariants on the current subject. Otherwise hold the route or quarantine the worker. Verify the restored state using prohibited and legitimate probes, and record which traffic remains held. Expiry or revocation blocks new activation of that release and triggers local re-evaluation and a verified fallback. Restrictions stay in place until a safe transition is established. Verify restart and outage behavior for each adapter. [Tetragon persistent enforcement](https://tetragon.io/docs/concepts/enforcement/persistent-enforcement/), [Argo Rollouts analysis](https://argo-rollouts.readthedocs.io/en/stable/features/analysis/).

## Comparative experiment design

Use disposable, isolated Linux fixtures with synthetic data and no external network or production credentials. Every prohibited-effect probe is an explicit test operation against a fixture-owned file, process marker, synthetic service or transaction counter. Freeze the legitimate service contract, the forbidden effects and their severity, the deployment manifest, tests and thresholds before the comparative runs. Hold back benign traffic strata and fixture or topology variants from the policy authors until profiles and baseline policies are frozen. This tests controls defined before the failure scenarios are revealed.

| Arm | Configuration |
| --- | --- |
| **1. Unhardened application** | Same application build, fixture identity and dependencies, with no study-specific hardening. Record unavoidable platform defaults. The external lab boundary and synthetic resources remain identical in every arm. |
| **2. Conventional least privilege** | A competent platform operator configures non-root execution, dropped capabilities, no privilege escalation, read-only root with required writable mounts, runtime-default seccomp, minimal service credentials and native network allowlists. Include a locally standard mandatory access control baseline where supported. Freeze the configuration before holdout evaluation. |
| **3. Aegis preventative profiles** | Preserve arm 2's floor. Use the same platform controls to express tighter workload-specific requirements and add scoped WAF or flag rules where the service contract supports them. Apply the proposed resolution, evidence and rollout workflow. Test architecture A first, and treat B and C as prespecified follow-on variants. |

Run a **matched-control comparison** as well. An operator applies the identical arm 3 effective settings through normal platform tooling, with the same scope, approval, canary criteria and independent probes. Compare coverage, disruption and recovery timing against profile-driven application. The core comparison estimates the value of the whole profile package. The matched comparison isolates workflow effects from the benefit of enabling extra controls.

| Experiment | Fixture and independent measurement |
| --- | --- |
| **E1. Process and file isolation** | Use a renderer that must complete a job using a writable scratch directory. A bounded fixture operation tries to start an inert helper and change a protected fixture volume. Check a separate process-start marker and the volume's contents and metadata outside the workload. Test cold start, a maintenance job, existing handles and a supported alternate mount layout. On matching platforms compare launch-time seccomp and the applicable AppArmor or SELinux policy. Add a live pre-effect eBPF variant when supported. |
| **E2. Service and egress isolation** | The workload needs a resolver and job broker. Compare delivery of inert test messages to those allowed peers and to synthetic forbidden peers. Count receipts at the destination with a separate observer. Include new and preexisting sessions, internal callers, rescheduling and both address families where available. Include a permitted network peer requesting a disallowed service operation to distinguish network reach from service authorization. |
| **E3. Edge and feature controls under change** | A fixture emits an inert marker on a test-only export operation outside the allowed contract. Replay benign transactions and tagged synthetic checks through every declared ingress and worker path while applying a scoped WAF rule or disabling the optional feature. Check the fixture ledger and per-replica transaction success. Exercise flag cache staleness, body limits, a deliberate false-positive change, loss of a control-plane component and partial rollout. Measure whether rollback preserves the prohibited-effect restriction and how much legitimate service remains. |

Block trials by workload, platform and topology. Use at least two recorded Linux configurations with different enforcement support, and pair arms by fixture seed, test corpus, resource budget and offered load. Randomize order within each block and reset replicas, connections, volumes and policy state between trials. Compare cold rollout, cached rollout and steady state independently. Start with 30 paired repetitions per planned platform-scenario block to assess variance and feasibility. Size a follow-up for the disruption budget and desired tail precision. Preserve pinned image and policy digests, topology, versions, ordered timestamps, raw observations and workload seeds for replay.

### Primary outcomes

- **Prohibited effects prevented.** Count independently confirmed no-effect attempts divided by all scheduled attempts for which the paired positive control demonstrates the effect. A candidate hold or rejection can count as prevention when an independent sensor confirms no effect. Unsupported targets, setup failures and missing observations receive no prevention credit. Report them separately alongside actual escaped effects, and disclose excluded cases whose positive control failed. Also report verified coverage as verified in-scope target/path pairs over all planned pairs. Report paired differences and confidence intervals, clustering by independent trial or deployment. Report severe effects individually.
- **Legitimate traffic disruption.** Divide legitimate transactions with incorrect outcomes, blocks, errors or deadline breaches by offered legitimate transactions. Include refusals before workload admission and optional features users expect to work. Break down results by workload operation and by rollout phase, and report p50/p95/p99 latency for successful legitimate transactions, plus readiness and availability during fallback. An initial research gate is zero observed effects for declared severe invariants and a one-sided 95% upper confidence bound of at most 0.1 percentage points on the increase in disrupted legitimate transactions over arm 2. Zero observed effects supports a claim only about the sampled conditions.
- **Time to safe protection.** Start the adoption clock when each team receives the same workload handoff and authorized change window. Separately start the activation clock with a common authorized rollout trigger after policies and local approvals are ready. Use the test controller's monotonic clock to timestamp both starts and receipt of the checks that satisfy the gate. Stop each clock at the first point when the required coverage, prohibited-effect tests, legitimate-traffic budget and prescribed observation window all pass. Report time to first verified canary, verified fleet coverage and safe recovery to both healthy service and preserved restrictions. If a control was already effective at the trigger, mark it pre-protected and report its initial adoption cost. Arm 1 and any run that fails to reach the gate are recorded as never reaching it within the fixed observation horizon. Report completion fractions and time-to-event curves with incomplete runs accounted for. Give p50/p95/p99 only where estimable, with probe cadence and soak time visible. The repository's proposed 30-second gate concerns the separate verified-finding response clock. [Aegis acceptance plan](../acceptance.md).

Use the same measurement procedure for operator-driven and Aegis-driven rollouts. Include fault cases for missing node policy, control-plane outage, stale evidence and interrupted application. Treat holds that preserve a security invariant as valid safety outcomes and count their service cost. No experiment has been run for this report.

## Existing alternatives and limitations

| Existing system | Documented overlap |
| --- | --- |
| Kubernetes Pod Security Standards and Security Profiles Operator | Admission baselines and native profile creation, recording and distribution. Direct overlap with the launch-time portion of A. [Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/), [Security Profiles Operator](https://github.com/kubernetes-sigs/security-profiles-operator). |
| KubeArmor, Cilium and Tetragon | KubeArmor translates runtime policies to supported Linux enforcement backends. Cilium supplies network policy, including optional L7 controls. Tetragon supplies hook-dependent runtime enforcement. These are direct comparators or foundations for B. [KubeArmor runtime enforcer](https://docs.kubearmor.io/kubearmor/quick-links/kubearmor_overview/runtime_enforcer), [Cilium policy](https://docs.cilium.io/en/stable/security/policy/index.html), [Tetragon enforcement](https://tetragon.io/docs/concepts/enforcement/). |
| Palo Alto Networks Prisma Cloud Compute | Learned runtime container models and operator-configured prevent or block actions. Compare policy authoring effort, compatibility and independent outcome verification on the same fixtures. [Prisma Cloud Compute runtime policy API](https://pan.dev/compute/api/33-01/post-policies-runtime-container/). |
| OWASP CRS, AWS WAF, OpenFeature and Argo Rollouts | Established tooling for generic WAF rules, managed rule count and block modes, provider-neutral flag evaluation and measured canary rollout. These can implement parts of a profile lifecycle. [OWASP CRS](https://github.com/coreruleset/documentation/blob/main/content/2-how-crs-works/2-1-anomaly_scoring/index.md), [AWS WAF actions](https://docs.aws.amazon.com/waf/latest/developerguide/web-acl-rule-actions.html), [OpenFeature](https://openfeature.dev/specification/sections/flag-evaluation/), [Argo Rollouts](https://argo-rollouts.readthedocs.io/en/stable/features/analysis/). |
| gVisor and Firecracker | Established isolation boundaries that can serve as the substrate for C. [gVisor](https://gvisor.dev/docs/architecture_guide/intro/), [Firecracker](https://firecracker-microvm.github.io/). |

The potential Aegis contribution is a portable contract tying an exact deployment and effective policy to independent evidence and a tested safe fallback across layers. The source documentation establishes substantial overlap with existing tools. Competitive value depends on demonstrating faster verified adoption or better coverage at comparable disruption against a competent conventional baseline.

Effects available through legitimate application authority remain hard to prevent, including misuse of permitted credentials, business-logic errors and disclosure through sanctioned outputs. Shared trust in kernel, host, adapter, verifier and local administration bounds each claim. Portability may stop at the intent when a platform cannot enforce equivalent restrictions. More restrictive settings can break maintenance jobs, and a security-preserving hold can reduce availability. Finite tests support only the pinned workload, topology, observation period and paths exercised. The first research decision is whether architecture A offers measurable value in the three-arm and matched-control comparisons before taking on the complexity of B or C.
