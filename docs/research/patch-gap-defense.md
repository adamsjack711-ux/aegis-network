# AI patch-gap defense

AEGIS Research R3 · 2026-11-19

**Finding.** The patch gap is a measured operational problem, and controlled studies show that automated patch analysis can produce some working exploits within an hour. Existing platforms already cover fast inventory matching, emergency virtual patching, isolation, and automated response. Aegis has a narrower opportunity where independent operators need to reuse the same verified finding, retain local authority over the response, and prove which paths each deployment actually protected. The repository demonstrates signed distribution and local dry-run decisions. Aegis's effectiveness at closing the gap remains an experimental question. [Anthropic n-day evaluation](https://www.anthropic.com/research/n-days), [Verizon 2026 DBIR, figures 12–14](https://www.verizon.com/business/resources/T15a/reports/2026-dbir-data-breach-investigations-report.pdf), [Aegis architecture](../../architecture.md).

## Evidence and timelines

Track the first public security-relevant change, advisory publication, availability of a supported downstream fix, observed exploitation, independently verified temporary protection, and verified fixed-version deployment as separate events. A public source change can precede both the advisory and an installable update. Project Zero defines the patch gap as fix release to user installation. For a defender, a successful compensating control can shorten the period of reachable exposure while the patch gap itself stays open. [Project Zero disclosure policy](https://projectzero.google/2026/11/disclosure-policy.html), [Project Zero on downstream patch gaps](https://projectzero.google/2022/11/mind-the-gap.html).

| Evidence | Result | What it supports |
| --- | --- | --- |

[IEEE paper record](https://ptolemy.berkeley.edu/projects/truststc/pubs/381.html), [Berkeley project summary](https://bitblaze.cs.berkeley.edu/apeg.html). |

[Anthropic n-day evaluation, Firefox section](https://www.anthropic.com/research/n-days). |

**Planning assumption.** Treat immediate exploitation after the first public fix signal as a stress case. Project Zero explicitly describes zero elapsed time as a threat model. Use slower onsets too and report each result separately. The public evidence gives selected laboratory timings and evidence of operational use. It leaves typical production patch-to-exploitation latency, the AI-attributable share, and the probability of exploitation for any given fleet unresolved. [Project Zero 2026 policy](https://projectzero.google/2026/11/disclosure-policy.html), [GTIG trend study](https://cloud.google.com/blog/topics/threat-intelligence/vulnerability-discovery-and-exploitation-trends-in-the-ai-era).

## Where defense loses time

1. **Upstream to supported fix.** Dependencies, downstream backports, repackaged images, and appliance vendors can delay a supported build. Track the first public upstream signal and the actual availability of a compatible downstream package. A version string can conceal a backport. [USENIX study of the Android kernel patch ecosystem](https://www.usenix.org/conference/usenixsecurity21/presentation/zhang-zheng), [Project Zero downstream analysis](https://projectzero.google/2022/11/mind-the-gap.html).
2. **Signal to decision.** Advisory lag, stale inventory, transitive dependencies, ambiguous affected ranges, and missing service owners add investigation time. Monitor supported vendors' security bulletins and release channels alongside GitHub Security Advisories, OSV, and the CISA KEV catalog. Keep source publication, modification, first-seen, withdrawal, and local-receipt times. Deduplicate CVE, GHSA, and OSV aliases while retaining provenance. Match deployed versions, build digests, and vendor backports. Flag silent security-relevant releases for review with lower confidence and reconcile missed notices and inventory drift. [GitHub global advisory API](https://docs.github.com/en/rest/security-advisories/global-advisories), [OSV API](https://google.github.io/osv.dev/api/), [CISA's official KEV data mirror](https://github.com/cisagov/kev-data).
3. **Decision to deployment.** Verify whether the installed build is affected and the relevant interface or operation is reachable. Prioritize using confirmed exploitation, exposure, privileges, criticality, dependencies, and the cost of taking the service out of rotation. Use CVSS for technical severity, EPSS for a model estimate of exploitation in the next 30 days, and KEV as evidence of known exploitation. Preserve an explicit unknown state for stale inventory, missing reachability, or conflicting advisories. Assign an owner and deadline for both the temporary control and the permanent fix. [CISA SSVC guide](https://www.cisa.gov/sites/default/files/publications/cisa-ssvc-guide%20508c.pdf), [FIRST EPSS](https://www.first.org/epss/faq).
4. **Deployment to closure.** Compatibility tests, change windows, reboots, unavailable endpoints, failed canaries, and stalled rollouts can leave vulnerable instances after a rollout starts. Measure per-instance fixed-version and health verification, including new replicas and returning nodes. Track planned exceptions and temporary control coverage until the permanent fix is verified. [NIST enterprise patch management guide](https://csrc.nist.gov/pubs/sp/800/40/r4/final).

## Temporary protection and preventative hardening

| Control | When it helps | Where exposure can remain |
| --- | --- | --- |
| WAF or IPS virtual patch | A known operation crosses a covered inspection point and is visible to that control. Vendor-managed rules can shorten preparation and distribution time. | Uninspected traffic, other ingress paths, or app-level semantics outside the rule's visibility. Count only verified protected paths. [OWASP virtual patching](https://cheatsheetseries.owasp.org/cheatsheets/Virtual_Patching_Cheat_Sheet.html), [Cloudflare Log4j response](https://blog.cloudflare.com/cve-2021-44228-log4j-rce-0-day-mitigation/). |
| Feature shutdown, identity or network restriction, quarantine | An owner can disable an optional function, restrict a management plane, or isolate affected workloads while the fix is tested. | Internal or local paths can persist. Isolation can also deny legitimate service. Kubernetes NetworkPolicy behavior depends on plugin enforcement and the combined set of applicable policies. [Kubernetes NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/). |
| Preventative hardening | Before a specific disclosure, remove unused interfaces, make management private, and restrict service privileges or egress based on existing inventory, service dependencies, and business impact. | Required public functionality remains exposed to some classes of defect. Restricting downstream effects earns containment credit only where the experiment measures those effects. [NIST enterprise patch management guide](https://csrc.nist.gov/pubs/sp/800/40/r4/final), [Mandiant M-Trends 2026 executive edition](https://cloud.google.com/security/resources/m-trends-executive-edition). |

Use preapproved, scoped controls with an owner and a review deadline. Pilot changes on a canary and check both protective effect and ordinary traffic across all relevant control points. Recheck after restarts, policy updates, and rescheduling. Define the last verified safe state before rollout, with an escalation path if a control fails or expires while the vulnerable build remains installed. Retire temporary controls after the fixed build is independently verified. [OWASP virtual patching lifecycle](https://cheatsheetseries.owasp.org/cheatsheets/Virtual_Patching_Cheat_Sheet.html), [Argo Rollouts analysis](https://argo-rollouts.readthedocs.io/en/stable/features/analysis/).

**Verdict.** The deployment gap is real. The strongest case for Aegis is a heterogeneous fleet or federation where one operator's evidence must be reusable across separate trust domains and local owners need auditable proof of both enforcement and safe rollback. A conventional stack can cover much of this with integrations. Whether Aegis can deliver the full workflow with better coverage or lower coordination cost remains open. Within a single well-integrated vendor environment, the documented capabilities give less reason to add Aegis. [Cortex playbooks](https://xsoar.pan.dev/docs/reference/packs/Rapid-Breach-Response), [Microsoft endpoint mitigations](https://learn.microsoft.com/en-us/defender-vulnerability-management/tvm-block-vuln-apps).

In the committed baseline at `14440ee`, Mesh distributes signed findings and Rapid checks the publisher, exact inventory match, and local template policy before recording its decision. The current path ends at dry-run. An independent verifier, evidence binding, an executor, health checks, and rollback remain prerequisites for a measured Aegis protection claim. Keep distribution-to-audit latency as a separate instrument. [Architecture](../../architecture.md), [acceptance gates](../acceptance.md).

## Controlled experiment

**Question.** How much reachable exposure does faster post-release mitigation remove, and what additional protection does pre-disclosure hardening buy at the same service and resource budget? Use a matched, isolated lab with synthetic services and benign markers. Each fixture emits a harmless event when a modeled boundary admits an operation, such as reaching a private management route or making a connection to a local stub. A simulated fix removes the fixture condition. Use synthetic timelines or archived advisory timestamps and metadata only. The oracle uses benign probes and control telemetry throughout.

**Hypotheses.** Reactive mitigation should reduce exposure where a verified signal arrives before the fix can be deployed and a temporary control covers the relevant path. Preventative hardening should gain the most when onsets are immediate and risky paths can be removed in advance. Required functions with no eligible control should still depend on patch deployment.

| Arm | Policy |
| --- | --- |
| **A · Traditional vulnerability prioritization** | Match advisory to inventory, rank by severity, exploitation evidence, reachability, and business criticality. Use normal CI, staged deployment, and the existing emergency patch lane when its preset criteria are met. |
| **B · Rapid reactive mitigation** | Use A's patch path and the same approved deployment controls. Once a relevant release signal is verified, a conventional playbook can apply a preapproved WAF rule, disable a function, or restrict a workload. The patch proceeds on the same schedule as in A. |
| **C · Preventative risk-based hardening** | Before replay, spend a fixed budget shrinking high-risk reachable surfaces using inventory, pre-existing topology, and service criticality. Freeze the choices before disclosing held-out cases. After disclosure, use B's reactive and patch workflow. B versus A isolates rapid mitigation. C versus B isolates the incremental value of prevention. |

1. **Freeze a matched corpus.** Start with a pilot to estimate paired variance. Target at least 30 held-out cases across edge-visible HTTP, internal or egress paths, optional functions, required functions with limited mitigation, and cases with no eligible control. Include unaffected and already-fixed negative controls. Split by service family before calibration. Run each case across all three arms on fresh identical snapshots with matched load, initial inventory, pre-existing controls, operator staffing, budget ceilings, and change windows. Randomize arm order and rotate operators to limit learning effects. Freeze case manifests, seeds, ranking rules, and change budgets. Keep fixture ground truth and held-out evaluation probes with an independent evaluator.
2. **Replay identical release and demand schedules.** Use a 24-hour pre-release hardening window and a seven-day observation horizon from the first public signal, with a 30-day replay sensitivity check for slow patch lanes. Replay advisory-first, fix-signal-first, and delayed or unavailable downstream fixes. Evaluate synthetic onset at 0, 15 minutes, 1 hour, and 24 hours after the first public signal. Hold probe cadence constant between arms and sample exposure throughout the horizon. Use fixed replay-clock schedules for long windows and wall-clock timings for actual control application and verification, including a five-second wall-clock probe interval during rollout. Report the clocks separately and disclose replay speed and sampling resolution.
3. **Test failures.** Run baseline trials and matched variants with stale or wrong inventory, a corrected advisory, a disconnected site, a failed canary, and control expiry or rollback. Give each arm the same benign workload and failure schedule. Verify every intended instance and route from an independent observer, including direct and alternate origins. Credit mitigation only after three consecutive clean protective checks on all required paths at the declared cadence. Record the interval from last observed exposure to first clean check and count any reopening during the horizon. Record lost legitimate transactions during isolation as service disruption.
4. **Isolate Aegis's contribution.** After the execution acceptance gates are met, rerun B and C with Aegis and a conventional playbook wired to signed artifacts, site-owned policy, and progressive rollout. Give both the same feed timestamps, evidence, inventory, verification probes, native control APIs, and human approval policy. Include multiple independently administered sites with differing local permissions and legitimate opt-outs. Record exclusion reasons and retain denied or ineligible cases in fleet-level outcomes. A dry-run rehearsal can exercise the protocol and authorization checks. Score protection only with actual control enforcement in the synthetic lab. [Aegis acceptance gates](../acceptance.md).

| Metric | Measurement |
| --- | --- |
| **Time to protection** | Timestamp source signal, ingestion, local decision, enforcement acknowledgement, and first independently verified fleet protection. Report elapsed time from the first public signal and separately from receipt of a verified finding. Report the protected share at release and at each onset, the share ever protected, and time-to-event estimates including median and p95 where estimable, with right-censoring at day seven. Preprotected cases start protected at release. Report time to verified permanent remediation separately. |
| **Remaining exposure** | Primary endpoint is exposed asset-path-hours over seven days. At each interval, sum the hours each vulnerable instance-path pair remains reachable enough for the modeled boundary event. Include reopened intervals and publish both equal-weighted and preregistered criticality-weighted totals. Also report marker rates by onset and residual exposure by path type. Report unknown intervals and bound totals by treating them as exposed and protected in sensitivity analyses. |
| **Service disruption** | Measure failed or falsely blocked benign transactions, affected-service minutes, p95 latency change, and rollback time to a healthy safe state. Include planned function shutdowns and pre-release hardening disruption. Track the worst affected site alongside the fleet average. |
| **Defensive resource cost** | Track hands-on operator minutes, on-call interventions, CPU/GPU time, API spend, licenses, and integration and maintenance effort. Separate fixed onboarding and recurring costs. Include hardening, retesting, rollback, and retirement. Report cost per site-month and incremental cost per exposed asset-path-hour avoided at stated workload volumes. |

**Decision rule.** Pre-register budget and service limits before the held-out replay. As starting lab thresholds, require a 25% reduction in exposed asset-path-hours for each claimed improvement, a paired 95% confidence interval excluding zero improvement, at most a 0.1 percentage-point increase in failed benign transactions, adherence to each service's existing latency objective, and zero unauthorized changes or unsafe rollbacks. Use paired, scenario-clustered bootstrap intervals across workload families and publish per-stratum distributions and eligibility denominators. Use the pilot to set the actual sample size and budget. Aegis must meet the same service and authority gates and either achieve the exposure improvement over matched conventional B/C or cut hands-on effort by at least 25% with exposure within a preregistered 5% non-inferiority margin and lower total cost at a stated scale. These are proposed thresholds. The experiment is unrun.
